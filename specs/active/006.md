# SDD 006: "I Am Machine" MVP — DearPyGUI Control Plane + Agent Orchestration Architecture

**Status**: Active
**Version**: 2.0.0
**Last Updated**: 2025-12-14
**Owner**: Ableton-MCP / Antigravity Agents

## 1. Scope

This document specifies the system design for the MVP described in `specs/active/005.md`:

- Ableton Live 12.3.1 runs the **AbletonMCP Remote Script** (TCP JSON server).
- A local **FastMCP server** exposes Ableton operations as MCP tools.
- A **DearPyGUI app** is the primary developer control surface.
- The GUI orchestrates **Ollama‑backed deepagents/CrewAI** agents that act only via tools.

### 2.2 Design Principle: GUI-First Orchestration

The GUI is not a “viewer”; it is the **stateful operator console**:

- the user can stop/pause execution
- the user can approve risky actions (delete tracks, replace devices)
- the user can run verification gates after each milestone

## 3. Interfaces & Protocols

### 3.1 Ableton Remote Script Socket Protocol (Existing)

- Transport: TCP
- Host/Port: `localhost:9877` (default in `AbletonMCP_Remote_Script/__init__.py`)
- Payload: JSON object:

```json
{ "type": "set_tempo", "params": { "tempo": 136.0 } }
```

- Response: JSON object:

```json
{ "status": "success", "result": { "tempo": 136.0 } }
```

### 3.2 MCP Tool Protocol (Existing)

The FastMCP server exposes tools that internally call the Remote Script:

- `get_session_info`
- `get_track_info(track_index)`
- `create_midi_track(index=-1)`
- `create_audio_track(index=-1)` (if available)
- `set_track_name(track_index, name)`
- `create_clip(track_index, clip_index, length)`
- `add_notes_to_clip(track_index, clip_index, notes)`
- `load_instrument_or_effect(track_index, uri)`
- `get_device_parameters(track_index, device_index)`
- `set_device_param(track_index, device_index, param_index, value)`
- rack/chain tools (rumble construction), where supported

**Design requirement**: orchestration should call these tools through a single adapter layer so the UI/agents never depend on raw tool names.

## 4. Orchestration Model

### 4.1 State Machine

The orchestrator is a state machine with explicit transitions:

- `IDLE` → `CONNECTED` → `BOOTSTRAPPED` → `RUNNING`
- `RUNNING` ↔ `PAUSED` (HITL gate)
- `RUNNING` → `ERROR` (recoverable) → `PAUSED` (review) or `RUNNING` (retry)
- `RUNNING` → `DONE`

### 4.2 deepagents as “Brainstem”, CrewAI as “Organs”

- deepagents provides:
  - todo list discipline
  - filesystem persistence
  - subagent routing
  - predictable loop control (plan → act → verify)
- CrewAI is optional and only used when role specialization increases quality (e.g., mixing heuristics).

### 4.3 Deterministic Recipe Layer (Critical)

Recipes are code, not prompts. Agents may *select* and *parameterize* recipes, but the recipe logic is implemented in Python.

Examples:

- `build_kick(track=0)` generates a fixed kick pattern and ensures device chain.
- `build_rumble(track=1, source_track=0)` builds the rumble rack/chain and sets sidechain.

## 5. DearPyGUI Integration Design

### 5.1 Concurrency Model

- DearPyGUI runs on the main thread.
- Orchestration runs in a background thread with its own asyncio loop.
- Communication is via an in-process event queue:
  - UI sends “commands” (Run/Pause/Stop/Step, Build Track N)
  - Orchestrator sends “events” (log lines, progress updates, verification results)

### 5.2 Required UI Panels (MVP)

- Connection + configuration panel (host/port, model selection)
- Track progress list (16 rows)
- Action buttons (Run All / Pause / Stop / Verify / Export)
- Log + error panel (tail of `events.jsonl`)
- Verification report panel (boolean checks + score)

## 6. Persistence & Filesystem Layout

All state is stored under a single project directory (see PRD §8.2):

`live_set/lily_palmer/i_am_machine/workspace/`

Notes:

- Code (recipes, helpers, track builders) live in `live_set/lily_palmer/i_am_machine/`.
- Runtime artifacts must be written only under `live_set/lily_palmer/i_am_machine/workspace/`.

Required files:

- `project_spec.json`: immutable desired target spec (checked into repo or generated once)
- `state.json`: mutable current state (what’s already applied)
- `events.jsonl`: append-only log (MCP tool calls + results + exceptions)

Optional:

- `exports/`: rendered WAVs, screenshots, analysis results
- `device_maps/`: resolved parameter name/index maps

## 7. Safety, Guardrails, and Security

### 7.1 Tool Allowlist

The orchestrator must expose a strict allowlist of DAW tools. LLM output can only:

- choose among allowed actions
- fill structured parameters validated by Pydantic

No arbitrary filesystem writes outside `live_set/lily_palmer/i_am_machine/workspace/` and no arbitrary shell execution.

### 7.2 Risky Actions Require HITL

- deleting tracks
- replacing an existing device chain
- loading external samples

## 8. Verification Strategy

### 8.1 Online Verification (DAW State)

Verify through Ableton-MCP state queries (tempo, track count, track names, device presence).

### 8.2 Offline Verification (Audio)

Optional stretch: render stems/2‑mix and compare against a user-provided reference using:

- `app/visualizer` (DearPyGUI audio visualizer) for spectral/temporal inspection
- lightweight feature scoring (RMS, spectral centroid, low‑band energy)

## 9. Testing Strategy

### 9.1 Unit Tests (Fast)

- pattern generators (kick, hats, bassline)
- schema validation (ProjectSpec, TrackSpec, ClipSpec)
- idempotency logic for `ensure_*` functions

### 9.2 Integration Tests (Requires Ableton Running)

- connection handshake (Remote Script + MCP Server)
- “bootstrap 16 tracks” from an empty Live Set
- “build kick + rumble” basic chain creation

## 10. Open Questions / Known Gaps

- Do we need new tools for:
  - clip note inspection
  - nested device/rack chain inspection
  - reliable device parameter addressing by name
- How to support consistent sample loading across machines (URI + library path conventions).
