# PRD 005: "I Am Machine" MVP — 16-Track Recreation via Ableton-MCP + DearPyGUI

**Status**: Active
**Version**: 2.0.0
**Last Updated**: 2025-12-14
**Owner**: Ableton-MCP / Antigravity Agents

## 0. Executive Summary

**MVP Target**: Recreate Lily Palmer’s *“I Am Machine”* (Peak Time / Driving Techno) in **Ableton Live 12.3.1** as a **16‑track** Live Set using:

- **Ableton-MCP** (Remote Script + MCP Server) for deterministic DAW control
- **Custom Python** for “recipes” (patterns, device chains, validation)
- **DearPyGUI** as the primary developer control plane to orchestrate **Ollama‑backed deepagents/CrewAI** workflows

This MVP is a *developer tool* first: it should reliably build and verify the session structure, then iterate on sound/arrangement under human supervision.

## 1. Goals

### 1.1 Product Goals

- Provide a **single GUI** (DearPyGUI) that can:
  - connect to Ableton-MCP
  - initialize the Live Set
  - run the agent pipeline per-track (and “Run All”)
  - show progress + logs
  - run verifications and generate a pass/fail report
- Produce a reproducible **16‑track template** aligned to the target production style (kick/rumble core, industrial percussion, lead motif, FX transitions).

### 1.2 Engineering Goals

- Use a **spec-driven, gate-based workflow** (Architect → Critic → Builder → Sentinel) with explicit acceptance criteria per phase.
- Make track construction **idempotent**: rerunning “Build Track 02‑Rumble” should converge the project toward the spec rather than duplicating devices/clips.
- Keep Ableton stable: **no audio dropouts** and **no UI freezes** during agent execution.

## 2. Non-Goals (MVP)

- Shipping or distributing any copyrighted content, stems, or extracted vocals.
- Bit-identical recreation (MVP targets “structural + sonic‑recipe parity”, not a perfect clone).
- Third‑party plugins (VST/AU). Use Ableton stock devices and user‑supplied samples only.
- Full Arrangement View automation. MVP focuses on **Session View clip scaffolding** and repeatable recipes; arrangement is a stretch goal.

## 3. Target User & Primary Workflows

### 3.1 Target User

- Developer/producer with Ableton Live 12.3.1 who wants to iteratively build a track using local agentic tooling and deterministic DAW control.

### 3.2 Primary Workflows (Happy Paths)

1. **Connect & Bootstrap**
   - Open Ableton with AbletonMCP Remote Script enabled.
   - Start/verify MCP Server connection.
   - From DearPyGUI: “Connect” → “Initialize Project” (tempo/key/tracks).
2. **Kick + Rumble Pass**
   - Run track 01 Kick recipe + track 02 Rumble recipe.
   - Run verification checks; adjust parameters with HITL approval.
3. **Drums → Music → Vox/FX**
   - Run remaining track recipes in order; verify after each section.
4. **Save/Resume**
   - Save state to filesystem, restart, and resume with the same plan + context.

## 4. Constraints & Assumptions

### 4.1 DAW / Runtime

- Ableton Live **12.3.1**.
- AbletonMCP Remote Script runs inside Ableton’s embedded Python (version varies by Live build; treat as **DAW‑embedded** and keep it conservative).
- External tooling runs with repo Python (**3.13** via `.python-version`), managed via `uv`.

### 4.2 System Constraints

- Track budget: **exactly 16 tracks** (no extra helper tracks in MVP).
- Default communication: `localhost:9877` (Remote Script TCP). MCP Server uses FastMCP.
- Offline-first: **Ollama** local inference is the default; no network access required for MVP.

### 4.3 Legal / Content Constraints

- Any “Vocal Main / Vocal FX” content must be **user‑supplied and licensed**. The system must not require extraction from the reference master.

## 6. Functional Requirements (FR)

### 6.1 DearPyGUI Control Plane

- **FR-001 (Connect/Disconnect)**: GUI can connect/disconnect to Ableton-MCP and display connection state.
- **FR-002 (Initialize Project)**: GUI can apply session defaults:
  - tempo: `136.0`
  - time signature: `4/4`
  - global project name: “I Am Machine (MVP)”
  - create and name the 16 tracks per §5
- **FR-003 (Per-Track Orchestration)**: GUI can run “Build” actions per track and show progress (0–100%).
- **FR-004 (Run All / Stop / Pause / Step)**: GUI supports long-running orchestration with:
  - stop (hard cancel at safe boundary)
  - pause (HITL review)
  - step (execute next planned action)
- **FR-005 (Logs & Audit Trail)**: GUI shows an append-only event log and writes it to disk as JSONL.
- **FR-006 (Save/Load State)**: GUI can save and restore:
  - current plan / todo list
  - per-track completion state
  - parameter “knob snapshots” (where supported)

### 6.2 Agent Orchestration

- **FR-007 (Ollama Backend)**: orchestration can run using a local Ollama model (configurable).
- **FR-008 (deepagents + CrewAI Support)**:
  - deepagents is the *stateful orchestrator* (planning, todo, filesystem)
  - CrewAI is used optionally for *role-based subagents* (e.g., “Mix Engineer”)
- **FR-009 (Tool-Only Actions)**: agents must not “freehand” DAW edits; all DAW modifications must occur via the Ableton-MCP tool layer.

### 6.3 Ableton-MCP Integration

- **FR-010 (Tool Coverage for MVP)**: the tool surface must support:
  - create MIDI/audio tracks, set names, set tempo
  - create MIDI clips and add notes
  - load instruments/effects by URI, build rumble rack chains, and set device parameters
  - query session + track info for verification
- **FR-011 (Idempotent Ensures)**: higher-level “ensure_*” operations must be defined:
  - `ensure_track(name, kind)`
  - `ensure_clip(track, slot, length)`
  - `ensure_devices(track, chain_spec)`

## 7. Non-Functional Requirements (NFR)

- **NFR-001 (DAW Safety)**: no blocking operations on Ableton’s main thread; keep command rate bounded.
- **NFR-002 (Latency Budget)**:
  - simple commands (e.g., `set_tempo`) should complete in < 250 ms on localhost
  - multi-step recipes (e.g., rumble rack build) may take longer, but must not freeze Live
- **NFR-003 (Recoverability)**: if the orchestration process crashes, it can resume from disk state without redoing completed work.
- **NFR-004 (Offline-first)**: all core flows work without external network.
- **NFR-005 (Determinism / Repeatability)**: recipe functions produce identical outputs given the same inputs unless intentionally randomized (and then randomness is seeded + logged).

## 8. Data Contract (Engineering Requirement)

All agents operate on structured “project spec” data. This reduces token usage and prevents invalid tool calls.

### 8.1 Canonical Models (Pydantic)

The following shapes are the contract between orchestration code and Ableton-MCP tools.

```python
from __future__ import annotations

from pydantic import BaseModel, Field
from typing import Literal


class FrequencyRangeHz(BaseModel):
    low_hz: int = Field(ge=20, le=20000)
    high_hz: int = Field(ge=20, le=20000)


class NoteSpec(BaseModel):
    pitch: int = Field(ge=0, le=127)
    start_time: float = Field(ge=0)     # beats
    duration: float = Field(gt=0)       # beats
    velocity: int = Field(ge=1, le=127)
    mute: bool = False


class ClipSpec(BaseModel):
    clip_index: int = Field(ge=0)
    length_beats: float = Field(gt=0)
    name: str
    notes: list[NoteSpec] = Field(default_factory=list)


class DeviceParamSpec(BaseModel):
    name: str
    value: float


class DeviceSpec(BaseModel):
    """A device to load and (optionally) set parameters for."""

    # For MVP we use browser URIs where possible; otherwise fall back to name-based matching.
    device_name: str
    device_uri: str | None = None
    params: list[DeviceParamSpec] = Field(default_factory=list)


class TrackKind(Literal["midi", "audio"]):
    pass


class TrackSpec(BaseModel):
    index: int = Field(ge=0, le=15)
    name: str
    kind: Literal["midi", "audio"]
    role: str
    element: str
    spectral_range: FrequencyRangeHz | None = None
    devices: list[DeviceSpec] = Field(default_factory=list)
    clips: list[ClipSpec] = Field(default_factory=list)


class ProjectSpec(BaseModel):
    name: str
    tempo_bpm: float = Field(ge=20, le=300)
    time_signature: Literal["4/4"] = "4/4"
    key_root: str = "F"
    key_mode: Literal["minor"] = "minor"
    tracks: list[TrackSpec] = Field(min_length=16, max_length=16)
```

### 8.2 Filesystem Contract

The orchestration layer must persist all artifacts under a single project root:

`live_set/lily_palmer/i_am_machine/workspace/`

- `project_spec.json` (the target spec)
- `state.json` (current state: what has been applied)
- `events.jsonl` (append-only audit log: tool calls + results)
- `exports/` (renders, screenshots, comparison audio — optional)

Notes:

- Code-owned “recipes” (track builders, helpers) live alongside the project under `live_set/lily_palmer/i_am_machine/`.
- Generated artifacts and run state must be written only under `live_set/lily_palmer/i_am_machine/workspace/`.

## 9. Verification & Acceptance Criteria (AC)

### 9.1 MVP Acceptance (Boolean Checks)

The Verifier must generate a report with the following minimum checks:

- **AC-001**: session tempo is `136.0 ± 0.1`
- **AC-002**: exactly 16 tracks exist
- **AC-003**: tracks 1–16 exist and match the canonical names in §5
- **AC-004**: track 01 has a clip in slot 0 with length 16 beats (4 bars)
- **AC-005**: track 02 contains the rumble processing chain (see §9.2)

### 9.2 Rumble Chain Definition (Required for AC-005)

The rumble must be an **audio texture derived from the kick** with this minimal chain:

1. Reverb (100% wet in the rumble chain)
2. Distortion/saturation (Roar or Saturator)
3. Low-pass / band-limited filtering (Auto Filter / EQ Eight)
4. Sidechain compressor keyed to the kick (pumping)

### 9.3 Tooling Gaps (Required Work)

Some checks require deeper inspection than `get_track_info` currently provides:

- clip note inspection (kick pattern correctness)
- nested devices inside racks/chains
- sidechain “enabled + source” verification by parameter name

These are **explicit MVP engineering requirements**: if missing, they must be added to the Ableton-MCP tool surface before AC can be automated end-to-end.

## 10. Risks & Mitigations

- **Device/URI mismatch across installations** → prefer URIs when available; implement fuzzy browser search fallback; log resolved URIs.
- **Parameter addressing instability** → build a “device parameter map” per Ableton version and store it under `live_set/lily_palmer/i_am_machine/workspace/device_maps/`.
- **DAW stability** → command queue + rate limiting; avoid long synchronous operations inside Ableton main thread.
- **Agent unreliability** → enforce todo-driven execution, tool-only actions, and a strict verifier gate before progressing to the next track.

## 11. Milestones (High-Level)

- **M0**: DearPyGUI can connect + initialize 16-track template (tempo + naming).
- **M1**: Kick + Rumble recipes implemented + automated verification.
- **M2**: Remaining drums implemented (tracks 03–09) + verification.
- **M3**: Music + vocal/FX scaffolding (tracks 10–16) + verification.
- **M4**: “Run All” from blank set produces a consistent baseline project and report.
